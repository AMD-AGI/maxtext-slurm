01 执行层级:软件怎么组织并行

你写一个 kernel,启动时指定"多少个 workgroup、每个多少 work-item"。硬件把它们拆成 wavefront 批量执行。点开每一层看清楚。

一次 kernel launch 的全部工作 = 一个 grid。grid 由很多 workgroup 组成。你在 host 端用 <<<grid, block>>>(CUDA)/ hipLaunchKernel 指定形状。同一 grid 内 block 的执行顺序无保证。
一组能协作的线程:它们跑在同一个 CU/SM 上,能共享 LDS(shared memory)、能用 barrier 同步。 不同 workgroup 不能互相 barrier、不共享 shared memory。调度到 CU 的顺序由硬件决定 → 非确定的根源。
硬件真正的调度单位:一批 lane 锁步(SIMT)执行同一条指令。 AMD wavefront = 64 lane(gfx9/CDNA);NVIDIA warp = 32 lane。 一个 workgroup 被切成若干 wavefront。分支发散(divergence)就发生在这一层内。
最小执行粒度,一条 SIMT lane。有自己的寄存器与程序计数器(逻辑上)。 "thread" 在 GPU 语境≠CPU 线程——它极轻量,成千上万个同时存在。
包含关系: GPU ⊃ CU/SM ⊃ (驻留的) workgroup ⊃ wavefront/warp ⊃ work-item/thread。 注意 workgroup 是软件概念,CU 是硬件概念——一个 CU 可同时驻留多个 workgroup(取决于 occupancy)。

02 硬件与调度:workgroup 怎么被派到 CU(非确定的来源)

GPU 里有很多 CU(compute unit)。你启动的 workgroup 数量通常远多于 CU 数, 硬件调度器动态地把 workgroup 分派到空闲 CU 上——顺序和时机每次运行都可能不同。点"派发"多跑几次感受一下。

8 个 workgroup → 4 个 CU
为什么这会导致非确定? 如果多个 workgroup 要 atomicAdd 到同一个 global 地址, 它们完成、写入的先后顺序 = 上面这个随机派发/执行顺序。浮点相加不满足结合律 → 顺序不同 → 结果尾数不同。 这正是 flash-attention 反向 dQ 抖的机制。

03 内存层级与作用域(atomic 打在哪一层很关键)

越靠上越快越小越私有,越靠下越慢越大越共享。atomicAdd 的"竞争范围"取决于变量在哪一层。

Registers
私有,无竞争,天生确定(如 dK/dV 的寄存器累加)。
LDS / Shared
workgroup 内共享。block-scope atomic 只在组内竞争。
Global / HBM
全 device 可见。device-scope atomic 跨所有 workgroup 竞争 → dQ 非确定。

04 Stream:另一种并发,别和 block 搞混

Stream 是 host 端的概念:它是一条"kernel/拷贝按提交顺序排队执行"的队列。 和 block/warp(device 端、单 kernel 内的并行)是两个不同层面的东西。

Block / Warp(device 内并行)

  • 发生在单个 kernel launch 内部
  • 同一个 stream、同一个 GPU
  • 成千上万个并行,顺序由硬件调度
  • dQ 的 atomicAdd 竞争就在这一层(跨 workgroup)

Stream(host 端并发)

  • 不同 kernel 之间的排序/重叠
  • 同一 stream 内:按提交顺序串行
  • 不同 stream 之间:可并发/乱序(另一类非确定来源)
  • 与单个 kernel 内的 dQ 竞争无关
一句话: stream 决定"哪个 kernel 先跑"(host 级);block/warp 决定"一个 kernel 内部怎么并行"(device 级)。 dQ 的非确定是后者——单 kernel 内跨 workgroup 的 atomicAdd 顺序,和 stream 完全无关。多 stream 是另一个独立的非确定来源。

06 最容易混淆的几对

workgroup ≠ CU

workgroup 是软件分组,CU 是硬件单元。不是 1:1——一个 CU 可同时驻留多个 workgroup(受寄存器/LDS/occupancy 限制), workgroup 总数通常也远多于 CU 数,分批轮转执行。

thread(GPU) ≠ thread(CPU)

GPU 的 work-item 极轻量、以 warp/wavefront 为单位锁步 SIMT 执行,成千上万个并存; CPU 线程重、独立控制流、数量少。别用 CPU 直觉想 GPU thread。

warp ≠ block

block(workgroup)是你指定的逻辑分组;warp/wavefront 是硬件把 block 自动切分的调度批次(32 或 64 lane)。 一个 block 含多个 warp。同步:block 用 barrier,warp 内隐式锁步。

stream ≠ block 并行

stream 是 host 端 kernel 之间的排序(粗粒度、跨 kernel);block/warp 是 device 端单 kernel 内的并行(细粒度)。 dQ 抖属于后者,与 stream 无关。

并行 ≠ 无序 = 非确定

并行本身不等于非确定。只有当并行的多方写同一处 + 合并顺序不定(atomicAdd)+ 操作不满足结合律(浮点)三者齐了才非确定。 去掉任一条件(独立缓冲 / 固定顺序 / 整数)都能恢复确定。

atomic 保证 ≠ 顺序保证

atomicAdd 只保证"不丢更新、不撕裂读写",不保证相加顺序。 顺序 = 运行时 workgroup 调度 → 这才是浮点结果抖动的根。

确定性判据(记这一条就够): 一个归约是否确定,只看 —— ①是否被拆到多个 workgroup?②若是,合并是 atomicAdd(无序) 还是 固定顺序归约? 单一写者 / 固定顺序 = 确定;跨 workgroup + atomicAdd = 非确定。
