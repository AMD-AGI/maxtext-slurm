为什么这套机制能做到 Deterministic?

反向传播里 dQ 的梯度累加原本用 atomicAdd,导致每次训练结果都不同。 本页用图、流程图和交互模拟,拆解非确定性从哪来,以及 split-buffer + 固定顺序归约 如何把它变成逐位可复现。

02 名词解释

点开每一项。理解这几个词,后面的机制就顺理成章了。

浮点加法有舍入误差,所以 (a+b)+c ≠ a+(b+c)。 结果取决于相加的顺序。这是所有非确定性的数学根源。
多个 GPU 线程块要往同一个内存地址累加时,用 atomicAdd 保证不丢数据。 但它的相加顺序 = 线程块到达的先后,由硬件调度决定,每次运行都不同 → 配合非结合律 → 结果抖动。
GPU 把计算切成很多线程块(block),分配到流多处理器(SM)上并行执行。 哪个 block 先算完、先写内存,没有保证的顺序。
注意力反向传播产出的三个梯度。dK/dV 每个 KV tile 由单一 block 独占累加(确定); dQ 每行要汇总所有 KV tile 的贡献(需跨 block 累加)。
Flash-attention 把 KV 序列沿长度切成宽度 kN0 的小块(tile)。 CK 里 kN0 = 128(当 head_dim≤128),否则 64。每块由一个线程块处理。
确定路径为每个 KV split 分配一个独立 dQ 缓冲,数量 nsplits = ⌈s_kv / kN0⌉。序列越长 → 分块越多 → nsplits 越大 → 显存越多。
GEMM 里的经典手法:把沿归约维(这里是 KV 轴)的求和拆成多份并行算, 再合并。合并若按固定顺序做,即得确定结果。
CK 的第二趟 kernel:读回 nsplits 个 dQ_accum 缓冲,对每个 query 位置 按 split 下标 0→n-1 的静态顺序求和,写出最终 dQ。顺序固定 = 确定。

03 张量视角:dQ 为什么必须"跨整个 KV 求和"

注意力的核心是分数矩阵 S = QKᵀ(形状 s_q × s_kv)。 前向 O = softmax(S)·V。反向时,query 行 i 的梯度 dQi 会用到 S 的第 i 行的全部列, 也就是所有 KV 位置 j 的贡献。

Q / dQ(query 侧) K / KV tiles query 行 i
关键直觉:dQ 的每一行都要接收来自所有 KV tile 的贡献。 而 kernel 为了 dK/dV 高效,是按 KV tile 并行的 —— 于是"多个 tile 的 block 同时写 dQ 同一行"就不可避免。

05 为什么只有 dQ 抖,dK/dV 不抖

同一个 kernel,写者数量不同,命运就不同。

dK / dV — 单一写者 ✓

dQ — 多写者 ✗

那前向呢?Oi 也是"对所有 j 求和",为什么它确定?

因为非确定不来自"求和"本身,而来自"求和被拆到多个 block 再用 atomicAdd 无序合并"。 同一个 Σj,换个并行布局,命运就不同。

前向 Oi — query 并行,单写者 ✓

顺序扫 KV tile 并累加(online-softmax) block i t0 t1 t2 t3 固定顺序 j=0→1→2→3(同一 block 内) O_i 寄存器内顺序累加 ⇒ 无 atomicAdd ⇒ 确定

反向 dQi — KV 并行,多写者 ✗

量求和维度并行方式谁在写同一输出确定?
前向 O_iΣ over j (KV)按 query 行单个 block(顺序扫 KV)✓ 天生确定
反向 dK_j/dV_jΣ over i (query)按 KV tile单个 block 独占✓ 天生确定
反向 dQ_iΣ over j (KV)按 KV tile多个 block → atomicAdd✗ 非确定
核心判据:"对所有 j 求和"前向后向都有,但它本身不制造非确定。 非确定 = 求和被拆到多 block + atomicAdd 无序合并。前向 O 每行由单 block 顺序求和(确定); 反向 dQ 因 KV-parallel 布局被拆开用 atomicAdd(非确定)。PR #508 就是把 dQ 的合并从"无序 atomic"改回"有序",让它像前向一样确定。
Caveat: 若前向用 split-KV / flash-decoding 变体(把单行的 KV 求和拆到多 block 再合并), 前向也可能非确定——但那是推理/长上下文小 batch 的优化,不是训练前向路径。CK 训练前向的源码审计显示 zero atomicAdd、zero cross-block reduction。

07 修复原理:两趟 kernel

把"N 个 block 并发 atomicAdd 到同一地址"改成"N 个 block 各写独立缓冲 + 一个 convert kernel 按固定下标顺序求和"。

自己的缓冲 —— 地址互不相交 ⇒ 纯 store,无竞争 Pass 2 · FmhaBwdConvertQGradKernel(固定顺序) for j in 0,1,2,3: dQ[i] += dQ_accum[j][i] 下标顺序写死,与调度无关 最终 dQ bit-exact ✓
为什么确定? ① 每个输出元素由独立映射归约,不再并发写同址;② 归约顺序静态固定(0→n-1)。 两个非确定来源同时被消除 ⇒ 每次浮点舍入路径完全一致。
PR #508 实际改动: CK 后端原本把 deterministic 参数写死成 false (fused_attn.cpp:491/680/866),修复就是把它真正传下去 → 触发上面的 split 路径。

08 代价:nsplits 份缓冲 = 显存墙

确定不是免费的。要为每个 KV split 存一份 fp32 dQ 缓冲: extra = nsplits × h_q × (b×s_q) × d_qk × 4B,其中 nsplits = ⌈s_kv / kN0⌉。 拖动滑块看它怎么爆炸。

nsplits64
额外 dQ 缓冲—
占 MI355X 单卡 HBM (192 GB)

对照 ticket:405B(seq8192,h128,b5,nsplits64)→ +169GB → OOM; 671B(seq4096,b16,nsplits32)→ +133GB → OOM。这就是你只能压 pdbs 的原因。

为什么不能简单 cap nsplits 省内存? 一旦 MAX_SPLITS < ⌈s_kv/kN0⌉,多个 block 又得共享同一 slot → 组内重新 atomicAdd → 确定性没了。 要既省内存又保确定,需两级有序归约(kernel 级改写),不是调个参数。
